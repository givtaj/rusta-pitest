# v0.1.0-alpha.5

Decoded-input and schema-complexity limits for OpenAPI suites and authored workloads.
Prepared release date: October 29, 2026. CLI and report interfaces remain alpha.

## Included

- Charge decoded UTF-8 string values and object keys against the configured
  JSON/YAML input budget, including each use of a YAML alias. Reject excess
  decoded content before copying it into the parsed document.
- Check expanded schema reference paths before compiling validators. Reject
  schemas exceeding 10,000 expanded schema visits or depth 64, including schema
  branches under legacy `dependencies`.
- Preserve supported productive recursion, reference sibling constraints,
  property-name dependencies, and unused schema declarations.
- Reject recursion that stays on the same instance value on any reference path,
  including paths through previously normalized schema targets.
- Exercise both limits through the built and extracted release executable,
  alongside the existing synthetic regression and release checks.

See [OpenAPI input and schema limits](../openapi-suites.md) and
[workload validation](../workloads.md).

## Compatibility and limitations

The CLI commands and report formats are unchanged. Inputs accepted by alpha.4
can now be rejected when their decoded text or expanded schema structure exceeds
the supported limits. YAML aliases are still supported within the input budget.
An explicit OpenAPI byte-budget increase can admit larger decoded inputs up to
the existing supported maximum; it does not relax the schema complexity limits.

These checks bound accepted input and schema structure. They are not a total
process-memory limit or a wall-clock limit on synchronous schema validation.
HTTP request timeouts do not provide such a validation deadline. No maximum safe
load, universal throughput baseline, or complete security audit is claimed.

The alpha.4 workload boundaries continue to apply: authentication and replay
inputs are static snapshots, writes require explicit opt-in, and the caller owns
target authorization, service lifecycle, fixtures, and cleanup. Generated OpenAPI
suites remain explicitly selected GET/HEAD checks. See the
[alpha.4 limitations](v0.1.0-alpha.4.md#known-limitations).

## Supported artifacts and release evidence

Supported binary targets remain Linux x86_64 on Ubuntu 24.04 or a compatible
glibc environment, and macOS arm64. Other targets are unverified. macOS binaries
are unsigned and not notarized. Distribution is through GitHub prerelease
archives; no crates.io publication is included.

Each archive includes the executable, documentation and examples, license and
security guidance, target-specific dependency notices, Rust standard-library
attribution, build provenance, and recursive internal checksums. Archive-level
SHA-256 sums accompany the release.

Publication requires all [release thresholds](../release-policy.md) on the final
revision: formatting, strict Clippy, all Rust/Python regressions on both supported
platforms, a fresh dependency audit, independent review, generated and verified
notices, and smoke checks of built and extracted binaries.

Before publication, record the final revision, successful CI and artifact runs,
security-analysis results, observed test counts, archive names, and verified
digests in the
[GitHub release entry](https://github.com/givtaj/rusta-pitest/releases/tag/v0.1.0-alpha.5).
This source document describes the candidate and does not assert that the release
has been published.
