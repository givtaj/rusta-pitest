# v0.1.0-alpha.8

`rusta-pitest workload capacity` measures which of the request rates and
burst sizes in a plan pass for one actor and one GET or HEAD operation. The
two results describe the tested target under the conditions of that run.

## How the sweep decides a level passed

Preview reads the plan without sending requests or resolving credentials.
Execution requires `--execute`, `--base-url`, and the plan's `--operation`.
Warmup drains before measurement. The runner then tests increasing sustained
rates and, separately, increasing synchronized burst sizes.

Every offered read must complete with a successful response that satisfies
the request's checks. A plan can also set `max_success_p95_ms`. Each search
stops at its first failing level or its configured ceiling and repeats its
last passing level twice, if one exists. A level is confirmed only when both
repeats pass. An uninterrupted execution exits zero when both searches
confirm a level and any requested report is saved.

The plan accepts up to 12 levels per search, 1,000 offered requests per
second, and 128 client slots. The total budget, including warmup and
confirmations, is at most 100,000 offered requests and 20 minutes of
scheduled trials and drain allowances. [Plan and report details](../workloads.md#capacity-sweeps)

## Reading a report

Capacity plans use `capacity_version: 1`. Dispatch report readers by both
`kind` and `schema_version`. Capacity reports use `workload_capacity` and
version 1. Authored `workload run` reports use `workload` and version 2.

In each of `sustained` and `bursts`, look for `first_failure` and
`highest_repeatedly_passing_level`. The latter is null if the first level or
either confirmation failed. Each trial records status counts, unsent reasons,
peak client requests in flight, and successful requests per second including
drain. Compare `successful_request_latency` with `all_attempt_latency` to
spot a low median caused by fast errors.

## Reproduce the bounded loopback sweep

Put the extracted alpha.8 executable on your `PATH`. From the root of the
alpha.8 source checkout or source archive, run the following with Python 3.
The script starts a loopback server on an ephemeral port, runs the packaged
CLI, checks its saved report, and shuts down the server.

```sh
rusta-pitest --version
out=$(mktemp -d)
python3 tests/fixtures/capacity/verify.py "$(command -v rusta-pitest)" "$out/capacity.report.json"
```

The fixture admits two concurrent slow reads and returns HTTP 503 quickly
for excess arrivals. Its checked-in sample confirmed 4 offered requests per
second and a burst of 2. At a burst of 6 it recorded two 200s and four 503s.
The sample's median latency was 42 ms across all attempts and 344 ms for
successful reads. Timing and observed overlap vary by run.
[Fixture and sample report](https://github.com/givtaj/rusta-pitest/tree/v0.1.0-alpha.8/tests/fixtures/capacity)
